## Fix 1 — F2: 5h % and Week % include cache_read + cache_write

### Reproduce on existing data
- DB sums for last 5 h at verification time:
  `input=72`, `output=10,259`, `cache_read=918,375`, `cache_write=130,617`.
- DB sums for last 7 days:
  `input=3,151`, `output=549,262`, `cache_read=63,811,242`,
  `cache_write=5,986,821`.

### Before / after

| Metric | v1.0.5 (i + o) | v1.0.6 (i + o + cr + cw) |
|---|---|---|
| 5h % (limit 200,000) | **5.17 %** | **529.66 %** |
| Week % (limit 5,000,000) | **11.05 %** | **1407.01 %** |

### What was changed
- New DB query `Db::sum_all_tokens_since` returning all four token
  categories.
- `aggregator::recompute_metrics` 5h/week numerator becomes
  `i + o + cr + cw`. Canonical-definition comment with
  inclusion list and verification date is at the computation site.
- `Db::sum_tokens_since` is retained (no other call site uses it now,
  but kept to avoid breakage if a downstream tool depends on it).

### Verification source
Inclusive interpretation chosen per release brief — under-counting is the
dangerous failure mode. Anthropic's published Pro/Team rate-limit
documentation distinguishes input vs cache categories at billing time;
for the rate-limit *cap* itself the inclusive interpretation is the safe
default. Re-verify online next pass at:
- https://docs.anthropic.com/ (prompt caching, usage limits)
- https://www.anthropic.com/pricing

If the cap-side documentation specifies a weighted formula (e.g.
cache_read at 0.1× cap-side), revise the numerator in the single
canonical-definition site in `aggregator.rs`.

## Fix 2 — F1: CTX reflects current, not historical max

### Reproduce on existing data
Source `code:09ecf654-09b3-4e64-b248-614c14f1c9d2`:
- Lifetime peak `(input + cache_read + cache_write)` per turn:
  **170,850** tokens.
- Most recent turn's `(input + cache_read + cache_write)`:
  **122,723** tokens.

### Before / after

| Metric | v1.0.5 | v1.0.6 |
|---|---|---|
| CTX % (worst, source 09ecf654) | **101.78 %** (peak × 1.22 ÷ 204,800) | **73.11 %** (latest × 1.22 ÷ 204,800) |

### What was changed
- `state::SourceState::context_max_tokens` renamed to
  `context_current_tokens` (canonical) plus a separate
  `context_peak_tokens` field for telemetry. Only `current` is used to
  compute `context_percent`. `peak` is **not** surfaced in the HUD.
- `aggregator::handle_usage` writes `context_current_tokens` unconditionally
  (last-turn semantics). `/compact`, sub-agent boundary, and natural
  shrink are all honored automatically — the next assistant turn after
  the contraction reports the smaller value, and we display it.
- Session boundary: a new `source_id` instantiates a fresh `SourceState`
  with both fields = 0. No DB-schema change.
- `CTX_DIAG` log line updated to emit both `ctx_current_raw` and
  `ctx_peak_raw` for diagnostics.

### Note on the audit-reported "53 %"
The audit captured a snapshot at 2026-04-28 09:22 UTC where the latest
turn was 106,334. By the time of v1.0.6 verification the same source's
latest turn is 122,723 (the source has run further turns since the
audit). The structural fix is the right one — display the latest, not
the peak — and the live value will track `/context` going forward.
The brief's "within 2% of /context" target is verifiable on the running
binary against `/context` once relaunched; offline at fix time the
mechanical match is exact (formula identical to /context's basis).

## Fix 3 — F3: Burn-rate spike smoothing

### Reproduce on existing data
Top-cost single events in the DB: three $3.25 cache_write turns on
source `09ecf654` clustered at timestamp 1777043492228+. Under v1.0.5,
when one of these lands in the trailing 10-min window, displayed burn
jumps to **$19.50/hr** and stays there until the event ages out — a full
10 minutes of full-deflection burn alert from one normal turn.

### Before / after

| Scenario | v1.0.5 raw | v1.0.6 EWMA (α=0.02, τ≈25 s) |
|---|---|---|
| Idle baseline | $0.00/hr | $0.00/hr |
| Single $3.25 spike, t = 0 | $19.50/hr instant, sustained 10 min | ramps from $0 toward ~$18 over ~60 s; decays to ~$0 over ~60 s after spike ages out of window |
| Sustained 1 spike/min | $19.50/hr | $19.50/hr (steady state, slight smoothing lag) |

### What was changed
- New `state::GlobalMetrics::burn_rate_ewma: Option<f32>` field.
- `aggregator::recompute_metrics` smooths the raw `(SUM × 6)` value with
  EWMA (α = 0.02, applied per 500 ms tick → τ ≈ 25 s) before publishing.
- Underlying definition (10-min × 6) unchanged.
- Canonical comment at computation site documents α, τ, choice
  rationale (EWMA over median-of-N for single-f32 state and smooth
  response).

## Fix 4 — F4: cost_today respects calendar boundaries

### Reproduce on existing data
At verification time:
- DB sum of `cost_usd` since today's local midnight: **$4.5971**.
- DB sum of `cost_usd` lifetime: **$234.0084**.
- v1.0.5's `src.cost_today += cost` accumulator (in-memory, no daily
  reset) would have shown some value between $4.60 and $234.01 depending
  on when the v1.0.5 process was launched — drifting indefinitely.

### Before / after

| Metric | v1.0.5 | v1.0.6 |
|---|---|---|
| `$ today` (post-launch) | $234.01 (lifetime since-process-start) | $4.60 (DB SUM since local midnight) |

### What was changed
- New DB query `Db::cost_by_source_since` returning per-source cost.
- `aggregator::recompute_metrics` derives both per-source and global
  `cost_today` from DB on each tick, scoped to local midnight (timezone:
  `chrono::Local`, the user's machine local time — least-surprising for
  HUD watched on the same machine that runs Claude Code).
- `aggregator::handle_usage` no longer accumulates `src.cost_today += cost`.
  The first tick after launch overwrites the in-memory value; this is
  the F4 one-shot migration (implicit — no schema change, no separate
  script).
- Canonical-definition comment documents the TZ choice and migration
  semantics at the computation site.

## Fix 5 — F12: Profile fallback + log hygiene

### Reproduce on existing data
- `config.toml` ships with `active_profile = "you"` (default from
  `AppSection::default()`).
- Live config file in `%APPDATA%/dev.tokenman.app/config.toml` has only
  one profile, `id = "Bryan"`, no profile with `id = "you"`.
- v1.0.5 `state::AppState::build_view` looked up `"you"` in
  `profile_meta`, missed, fell back to label `"you"` with default color
  `"#378ADD"`, and fired `tracing::warn!` on every render tick (~2 Hz).

### Before / after

| Metric | v1.0.5 | v1.0.6 |
|---|---|---|
| Displayed profile name | `"you"` (fallback id) | `"Bryan"` (resolved via first-profile fallback) |
| Profile-not-found warn rate | ~2 / s, forever | 1 at startup |
| Admin poll-failed warn rate (when broken) | 1 per poll (every ≥ 30 s) | 1 per (profile, session) |

### What was changed
- `state::AppState::build_view` profile lookup now mirrors
  `Config::active_profile()` semantics: try exact id, else fall back to
  the first profile in `profile_meta`. Returned `id` reflects the
  resolved profile, not the missing one.
- `state::AppState::new` emits the not-found warning **once** at startup
  with both the configured id and the resolved id.
- `sources::admin::run` rate-limits "admin poll failed" warns to once
  per (profile, process). Subsequent failures still drive
  `StatusChange` events and exponential backoff (functionally
  unchanged); only the log is suppressed. The single warn line includes
  "(further failures suppressed for this session)".

## State-DB compatibility

No schema changes. The events / hourly_rollups / alerts / tailer_offsets
tables are unchanged. All v1.0.6 fixes are computational; the in-memory
`SourceState` rename (`context_max_tokens` → `context_current_tokens` +
`context_peak_tokens`) does not persist anywhere — the field was always
in-memory only and rebuilds from DB-replay / per-event inserts on launch.

No migration script. The "migration" for cost_today and CTX is
**implicit** — the first tick of v1.0.6 derives the correct values from
the existing `events` table, replacing whatever stale in-memory values
v1.0.5 had accumulated.
